# Troubleshooting Changesets

## First, collect the facts

```bash
node --version
pnpm --version        # or npm/yarn
changeset --version   # via the project's package-manager invocation
cat .changeset/config.json
cat .changeset/pre.json 2>/dev/null
ls .changeset/*.md
git status --short
git branch --show-current
git log --oneline -5
```

Most failures come from one of: wrong package names, a missing base branch, interactive commands in a non-interactive session, or registry permissions.

## Common errors

### `changeset init` hangs, or exits with "unsettled top-level await"

**Cause:** v3's `init` is interactive (it asks about GitHub changelog integration). With stdin closed — CI, subagents, piped commands — it cannot answer and fails.

**Fix:** do not run `init` non-interactively. Create `.changeset/config.json` directly using the default in `config.md`, or ask the user to run `changeset init` in their terminal. The `.changeset/README.md` generated by `init` is optional.

### `Failed to find where HEAD diverged from "main"`

**Cause:** the configured `baseBranch` does not exist locally, the clone is shallow, or the directory is not a git repository.

**Fix:**

```bash
git fetch origin main
git branch -a
git checkout main && git pull   # or fetch the branch without checking out
```

If the default branch is not `main`, set `baseBranch` in `.changeset/config.json` (e.g. `"master"`, `"develop"`, or a backport branch). For one-off commands, pass `--since <valid-ref>`. In a non-git directory, skip `status` and inspect changeset files directly.

### `version` exits with code 1 and says "No unreleased changesets found"

**Cause:** this is normal v3 behavior. It used to exit 0 in v2.

**Fix:** treat it as a no-op, not a failure. In scripts, check the exit code and message deliberately:

```bash
changeset version
code=$?
if [ $code -ne 0 ] && ! changeset version 2>&1 | grep -q "No unreleased changesets"; then
  exit $code
fi
```

More robustly, check for pending changeset files (excluding `.changeset/pre/` and config) before running `version`, or use `status --output`.

### `status` exits 1: changes detected but no changesets

**Cause:** the repository's CI policy requires a changeset for every changed package.

**Fix:** add a changeset for the consumer-visible change, or create an empty changeset if the change releases nothing:

```bash
changeset add --empty -m "Update CI configuration"
```

### Changeset names a package that does not exist

**Symptom:** version or status reports a missing/unknown package, or the changeset appears to do nothing.

**Cause:** the frontmatter uses a directory name or a typo instead of the exact `name` field from `package.json`.

**Fix:** read every `packages/*/package.json` and copy the `name` exactly. Remove stale entries for deleted packages:

```bash
grep -R '"my-deleted-package"' .changeset
```

Delete those lines; Changesets skips deleted packages, but stale entries can block versioning.

### The changeset affects a private package but nothing happens

**Cause:** v3 does not version private packages by default.

**Fix:** if the private package should be versioned/tagged:

```json
{ "privatePackages": { "version": true, "tag": true } }
```

If it should never be released, this behavior is correct; remove the package from the changeset.

### Publish fails with 403/404 or "access" errors

**Causes and fixes:**

- **First public publish of a scoped package:** npm defaults scopes to restricted. Set `"access": "public"` in config or `"publishConfig": { "access": "public" }` in the package.
- **Not authenticated:** run `npm whoami`; check `NODE_AUTH_TOKEN`/`.npmrc` in CI. With 2FA locally, pass `--otp`.
- **Wrong registry or scope ownership:** confirm the `.npmrc` registry for that scope and that the authenticated account owns the scope.
- **Package version already exists:** `publish` skips already-published versions; if the version was yanked/registry state is inconsistent, bump the version or contact the registry.

### Publish fails because of ignored packages

**Cause:** the `ignore` config (or `version --ignore`) has two safety rails:

1. A changeset mixes an ignored package with a non-ignored one.
2. An ignored package needs a dependency update as part of the publish.

**Fix:** split the changeset, remove the package from `ignore`, or make the dependency relationship consistent. `ignore` is for temporary holds; permanent exclusions belong in `"private": true`.

### A brand-new package was published unexpectedly

**Cause:** `publish` publishes any local version missing from the registry. This can happen via automated publish or snapshot jobs.

**Fix:** set `"private": true` on packages that must never publish, and run `changeset publish-plan` before publishing. If it already happened, use the registry's deprecation/unpublish policy carefully — npm's unpublish rules are restrictive and dependents may exist.

### Git tags are missing on the remote

**Cause:** `changeset publish` creates tags locally but does not push them.

**Fix:**

```bash
git push --follow-tags
```

If tags were created for the wrong commit, delete them locally and remotely and re-tag from the version commit.

### changesets/action cannot create the version PR

**Symptoms:** `remote: Permission to ... denied to github-actions[bot]`, `GitHub Actions is not permitted to create or approve pull requests`.

**Fix:** enable **Settings → Actions → General → Allow GitHub Actions to create and approve pull requests**, and grant the version job `contents: write` and `pull-requests: write`.

### The version PR exists but CI does not run on it

**Cause:** PRs created with the default `GITHUB_TOKEN` do not trigger subsequent workflows.

**Fix:** create a GitHub App token or PAT and pass it as `github-token` to the action. Also check that the version commit/merge commit does not contain `[skip ci]`, including from the `commit` config's `skipCI` setting.

### Versions are higher/lower than expected

**Causes:**

- Multiple pending changesets: `version` takes the highest bump per package.
- `fixed` groups force every member to the same version.
- `linked` groups version from the highest current version in the group.
- Prerelease mode is active (`.changeset/pre.json`).
- Dependents are patch-bumped automatically when a dependency leaves their range.
- Existing versions in `package.json` already drifted from the registry.

**Fix:** run `changeset status --verbose` before versioning; review the diff; remove stale changesets; check config.

### Internal dependency ranges were not updated

**Causes:**

- The dependent package itself is not being released — Changesets only updates ranges in packages that are part of the release.
- `updateInternalDependencies: "minor"` leaves ranges alone for patch releases.
- The dependency range is not a `workspace:` protocol and `bumpVersionsWithWorkspaceProtocolOnly: true` is set.
- The new version still satisfies the existing range (for `minor` mode).

**Fix:** add a changeset for the dependent package if its published metadata must change, or adjust `updateInternalDependencies`.

### `add` suggests no changed packages

**Causes:** base branch missing/shallow clone, wrong `changedFilePatterns`, changes already committed but `baseBranch` points elsewhere, or the directory is not a git repo.

**Fix:** fetch the base branch, pass `--since <ref>`, or specify packages explicitly with `--patch/--minor/--major`.

### Snapshot was published as `latest`

**Cause:** `changeset publish` without `--tag` uses `latest`.

**Fix:** immediately publish a corrected stable version with `--tag latest`, or use `npm dist-tag` to move `latest` back to the intended version. Always publish snapshots with `--tag <name> --no-git-tag` in the future.

### Prerelease versions do not satisfy expected ranges

**Cause:** prerelease versions such as `1.2.0-beta.0` generally do not satisfy `^1.0.0`, so dependents get patch bumps and range updates.

**Fix:** this is expected. Verify the released dependency graph with `changeset status --verbose` before publishing.

## Migrating from Changesets v2 to v3

Checklist:

1. **Runtime:** Node `^22.11 || ^24 || >=26`; pnpm `>=10`, npm `>=10.9`, yarn `>=4.5.2`. Yarn Classic is unsupported. Packages are ESM.
2. **GitHub Action:** upgrade to `changesets/action@v2` (v1 does not work with v3). Rename inputs: `version` → `version-script`, `publish` → `publish-script`, `commit` → `commit-message`, `title` → `pr-title`.
3. **Exit code:** `version` now exits 1 when there are no changesets; update scripts and snapshot jobs.
4. **Config:** `prettier` → `format`; `access: "private"` → `"restricted"`; snapshots option moved to `snapshot.useCalculatedVersion`; private packages are no longer versioned by default.
5. **CLI:** `changeset tag` → `changeset git-tag`; `--sinceMaster` → `--since`.
6. **Behavior:** peer dependency updates bump dependents by `patch` instead of `major`. Review dependents when adding changesets.
7. **pnpm:** registry detection follows pnpm and ignores scope-based `publishConfig.registry` overrides; use `.npmrc` instead.
8. **Prereleases:** versioned changesets move to `.changeset/pre/`; `pre.json` no longer lists IDs. Run `changeset status` once to migrate state.
9. **Bolt:** Bolt workspaces are no longer detected; migrate to pnpm/npm/yarn workspaces.

## Pre-publish safety checklist

Before running `changeset publish`:

- [ ] `git status` is clean and the last commit is the version commit.
- [ ] `changeset publish-plan` lists only the packages and versions you expect.
- [ ] Every intended package has `access`/`publishConfig.access` set correctly for a first publish.
- [ ] Packages that must never publish have `"private": true`.
- [ ] Prerelease/snapshot/backport publishes use an explicit `--tag`.
- [ ] `npm whoami` shows the expected account/registry.
- [ ] The user has confirmed the publish; it is irreversible.
- [ ] After publishing, run `git push --follow-tags`.
